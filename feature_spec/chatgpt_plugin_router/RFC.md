# RFC: Global MCP router for the ChatGPT plugin

This document is the mcp-server summary of that design; the Connection RFC stays the source of truth for the reasoning, the OpenAI evidence and the rollout.

**Gate still open.** The Connection RFC makes written confirmation from OpenAI, that a stack picker before the Keboola login is acceptable for the public Plugin Directory, the gate for this work (its Open Questions). The router is built before that answer, by decision of the RFC owner; nothing routes to it until the deployment task (3.5) and the public submission (4.3). If OpenAI says no, the RFC falls back to one plugin per stack and the router is not deployed.

## Problem

An OpenAI plugin has exactly one MCP server URL, and that URL cannot change after the plugin is published. Keboola runs one hosted MCP server per stack (`https://mcp.<stack>/mcp`, derived from `HOSTNAME_SUFFIX`), each of them its own OAuth authorization server brokering to its own stack's Connection. A single plugin URL can therefore serve the users of one stack only, and EU customers (three of the five multi-tenant stacks) could never use a listing pinned to US AWS.

## Required Behavior

A new run mode of the same image, `--mode=router`, serves the plugin's URL and sends each user to their own stack:

| Endpoint | Behavior |
|---|---|
| `/.well-known/oauth-protected-resource` | `resource` = router `/mcp`, `authorization_servers` = [router issuer] |
| `/.well-known/oauth-authorization-server` | Router issuer and endpoints, `S256`, `authorization_response_iss_parameter_supported: true` |
| `/register` | Answered locally, like the regional server: a fresh `client_id`, nothing stored |
| `/authorize` | The stack picker (one link per stack); with `stack=<key>`, 302 to the chosen stack's `/authorize` with every original parameter, `stack` dropped and `via=router` added. `stack=<key>` from the table skips the picker |
| `/token`, `/revoke` | Route by the stack key prefix of `code`, `refresh_token` or `token` (`eu-aws.<value>`), body forwarded unchanged. Unknown prefix: `/token` answers `invalid_grant`, `/revoke` answers 200 (RFC 7009), no upstream call |
| `/mcp` (3.2) | Reverse proxy by the prefix of the bearer token, streamed; 401 with `resource_metadata` without a known prefix |
| `/.well-known/openai-apps-challenge` | `OPENAI_APPS_CHALLENGE` as text, 404 when unset |

The router holds no Keboola credentials, no database and no session state, and never calls Connection. Its logs carry metadata only (method, path, status, stack key, latency), never a query string, a header or a body.

Regional servers (3.3) treat `/authorize` with `via=router` and `resource` = router URL as a router flow: same validation as today, `iss` = router issuer, the stack key prefixed on the code, access and refresh tokens they issue, prefixed tokens accepted at their `/token`, `/revoke` and `/mcp`, and the session bound to the router resource. Every other request is unchanged. Sessions bound to the router resource get the directory tool profile (3.4): an explicit allow-list without `run_sync_action`, `create_project` and `create_python_js_data_app_git_credential`, applied to `tools/list` on every path and to tool calls.

## Resolution Strategy

- Regional servers did not serve `/revoke` before 3.3; 3.3 enables it together with the prefixed tokens, which are the only tokens the router forwards there. Its handler is the server's own: the SDK's refuses a request without `client_secret`, which every (public) client of the server omits.
- Regional settings (3.3): `KBC_STACK_KEY` and `KBC_ROUTER_URL`, both or neither. A flow is a router flow only with `via=router` and the router's resource; it is then bound to that resource, its code and tokens carry the stack key, and `/token`, `/revoke` and `/mcp` take them with or without the prefix (the same session either way). Every other request, including the router's resource without `via=router`, is handled exactly as before (a foreign resource, logged or refused per `KBC_OAUTH_RESOURCE_BINDING`). Every authorization code JWT carries a `stack` claim, the minting server's stack key, and `/token` refuses a code whose claim is not its own: codes are stateless, so without it a code would redeem at any stack that shares the `jwt_secret` (3.5 also gives every stack its own).
- `src/keboola_mcp_server/router/` holds the mode: `stacks.py` (the stack table, the prefix, and `router_issuer()`/`router_resource()`, the one function pair the router and the regional servers both use to derive the router issuer and resource from the router URL, so the two sides cannot disagree), `settings.py` (environment only), `picker.py`, `rate_limit.py` and `app.py` (the Starlette app). `cli.py` adds `--mode`.
- One logical authorization server: the router serves the metadata, `/authorize` (the picker) and `/token`; the regional server that completes the login mints codes and tokens with `iss` = router issuer from the start, so the router never rewrites a response.
- The stack table defaults to the five multi-tenant stacks and can be replaced by `KBC_ROUTER_STACKS` (a JSON list), so a dev stack upstream and the one-by-one production rollout are configuration changes. Upstreams are validated as https origins; a redirect or a forwarded request only ever targets one of them.
- The picker is a server-rendered page of plain links, one per stack: `/authorize?<every original parameter>&stack=<key>`, the parameters parsed and re-encoded (so an encoded `&stack=` stays inside its value) and the link HTML-escaped; nothing else from the request is rendered. Not a form: browsers apply `form-action` to every redirect after a form submission (verified in headless Chrome 155), and the chain after the picker (router, the stack's `/authorize`, Connection's consent) leaves the router's origin, so a form under `form-action 'self'` could never log anyone in; a link navigation is not subject to it. CSP `default-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'; object-src 'none'`, `Referrer-Policy: no-referrer` (the page URL carries `state`), no script, the stylesheet served by the router. The choice is a 90-day first-party cookie that only highlights the last-used link. No CSRF token: the only state a link changes is the clicking browser's own cookie, and the redirect it yields is one the user could open by hand.
- Rate limits (Connection RFC, Security Considerations "Abuse / DoS") are process-local (no database), in one-minute windows, and keyed by who calls. `/authorize` is a person's browser: per client address, 60 per minute by default (`KBC_ROUTER_AUTHORIZE_RATE_LIMIT_PER_IP`). `/register`, `/token`, `/revoke` and `/mcp` come server to server from the AI client's few shared egress addresses, where a per-address limit sized for one user would refuse every plugin user at once, so `/token` and `/revoke` are limited per credential, by the SHA-256 of the presented code or refresh token (or token), 10 per minute by default (`KBC_ROUTER_TOKEN_RATE_LIMIT_PER_CREDENTIAL`); `/mcp` per hashed bearer token, 600 per minute by default (`KBC_ROUTER_MCP_RATE_LIMIT_PER_TOKEN`, 3.2); a token of an unknown stack is answered 401 without being counted. Past 100k distinct keys a minute, new codes and refresh tokens share an overflow bucket (1000 per minute and path), while `/mcp` fails open: an overflow bucket there would refuse the tool calls of every session not yet counted in the window, and random tokens let through only get a 401 from their stack. `/register` has only an optional per-address ceiling, `KBC_ROUTER_API_RATE_LIMIT_PER_IP`, sized from observed traffic by the deployment (3.5); the router warns at startup while it is unset. No credential reaches the limiter's memory or the logs, only its hash (logged shortened).
- Bodies of `/register`, `/token` and `/revoke` are capped at 64 KiB (413), repeated `grant_type`, `code`, `refresh_token` or `token` parameters are refused (`invalid_request`, so the router never routes by one value while the stack reads another), and Starlette's trailing-slash redirect is off, because it builds its `Location` from the request's `Host` header.
- `/mcp` (3.2) streams the stack's answer chunk by chunk (SSE included) and forwards only the bearer token and the MCP transport headers: one copy each of `Content-Type`, `Accept` and `Last-Event-Id`, and every copy of every `Mcp-*` header (`Mcp-Session-Id`, `Mcp-Protocol-Version`, and the `Mcp-Method`, `Mcp-Name` and `Mcp-Param-*` that a `2026-07-28` stack checks against the body, a repeated one included, so the stack refuses it as it would on a direct connection); a repeated `Authorization` is answered 400 `invalid_request`, since the router routes and counts by one token. Cross-origin, CORS allows any request header (`Mcp-Param-*` names come from each tool's schema), but only these reach a stack: no header selects a stack or reconfigures it. The stack's `WWW-Authenticate` never comes back, and a 401 from the stack becomes the router's own 401, so a client always rediscovers the router's authorization server. A stack silent for longer than `KBC_ROUTER_MCP_READ_TIMEOUT_SECONDS` (default 300, for long tool calls) gives 504 before the response starts and ends the stream after it.
- `/mcp` has its own upstream connection pool per stack (`KBC_ROUTER_MCP_MAX_CONNECTIONS`, default 1000 per stack and replica), so long tool calls and streams cannot starve `/token`, and a slow stack cannot starve the others; a full pool answers 503. One token may have at most 20 `/mcp` requests in flight per replica (`KBC_ROUTER_MCP_MAX_IN_FLIGHT_PER_TOKEN`, counted by its hash, released when the answer ends); above it, 429 with `Retry-After: 1`; a refused request still counts against the per-minute limit, which is counted first. The per-minute limit bounds the rate, not how long each request holds a connection, so without this cap one token with slow tool calls could hold its stack's whole pool. The deployment (3.5) must let idle responses live as long as the read timeout on the router's ingress and on every regional ingress, and give pods a shutdown grace period that fits open streams. The regional servers are stateless, so the router needs no session affinity; a stateful multi-replica stack would need its own ingress to pin replicas by `Mcp-Session-Id`, which the router forwards both ways (cookies are not).
- Uvicorn's access log is off in router mode because it would log the `/authorize` query string (`state`, the PKCE challenge).
- `/token` and `/revoke` forward `Content-Type`, `Accept` and `Authorization` (client authentication) with the verbatim body, and never `X-Forwarded-For`: the regional server sees the router's address, and a forwarded header would let a caller choose the address it counts.

## Scope

In scope: router mode (3.1, 3.2), the regional changes for router flows (3.3), the directory tool profile (3.4).

Out of scope: the deployment, hostname, DNS, TLS and kbc-stacks values (3.5), monitoring (3.6), the plugin package and its URL switch (Phase 1, 4.3), single-tenant stacks, CIMD, multi-region hosting of the router.

## Testing / Verification

- Unit tests per task (`tests/router/`, `tests/test_oauth.py`, `tests/test_mcp.py`): metadata values and issuer equality, picker escaping and CSP, redirect parameters and table-only upstreams, prefix routing and the local answers for unknown prefixes, logs without headers or bodies, rate limits, streamed `/mcp` responses, upstream timeout 504, both regional branches, the directory profile on every `tools/list` path.
- End to end (3.5, needs the deployment): a ChatGPT custom connector on the router URL against a dev stack: picker, consent, tool call, refresh, revoke; ingress logs and traces without `Authorization`, tokens or bodies.
